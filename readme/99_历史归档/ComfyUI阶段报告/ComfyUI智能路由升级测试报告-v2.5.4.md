## 1. 本次结论

1. “一张图片 + 一个独立音频”的报错不是素材损坏，而是 MiniMax H3 Turbo 在混合模态输入时发生张量分段数量不一致。原报错为：`tensor a (3) ... tensor b (2)`。
2. 同一张图片和同一个 MP3 改用原速 20 步后真实生成成功。按当前使用要求，多参工作流不再强制切换模式：前台选 Fast 就加载 Turbo LoRA，选原速则使用 20 步模板。
3. 首尾帧路由已经扩展为三合一：0 张图为纯文生视频，1 张图为首帧生视频，2 张图为首尾帧视频。
4. 附件缩略图新增媒体类型标识，并支持读取常见音频文件的内嵌封面。
5. 前台注册名称为 `minimax-h3-local` 和 `minimax-h3-Ref-local`，其他旧名称继续作为隐藏兼容别名使用。

## 2. 前台模型简称

| 简称 | 用途 | 输入规则 |
|---|---|---|
| `minimax-h3-local` | 文生 / 首帧 / 首尾帧智能路由 | 0、1 或 2 张图片 |
| `minimax-h3-Ref-local` | 多参考素材路由 | 图片、视频、音频任意组合，至少 1 个素材 |

旧工程中保存的 `minimax-h3-local`、`minimax-h3-first-last-local`、`minimax-h3-reference-local` 等名称仍能匹配，不要求立刻改旧字段。

## 3. 多参模式规则

- 所有单一或混合素材组合都遵从用户选择的加速 / 原速模式。
- Fast 使用 6 步 Turbo LoRA；原速使用 20 步质量模板。
- Fast 模板会加载 Turbo LoRA，但当前第三方 Turbo 插件在图片＋音频等混合参考下存在时间条件行统计不完整的问题，可能出现 `tensor 3 vs 2`。Lingwu 工程不修改第三方插件；在独立兼容组件完成前，混合多参需要稳定输出时应选原速。
- 返回任务信息中的 `mode` 会记录实际模式，便于排查。
- 视频自身的内嵌音轨仍不重复连接到参考音频端口，避免同一个视频被拆成额外模态段。

## 4. 首尾帧路由规则

- 0 张图：删除工作流中的首帧加载节点和 `first_frame` 连接，执行纯文生视频。
- 1 张图：图片作为首帧。
- 2 张图：第一张作为首帧，第二张动态注册为尾帧。
- 清晰度继续支持 `360P / 480P / 720P / 1080P`，也兼容 `0.3 / 0.7 / 0.78MP` 等原始百万像素数值。
- 首尾帧模板的音频链路原本完整存在：采样器音频 latent → 音频 VAE 解码 → `CreateVideo.audio`。
- 前台声音开关关闭时，只在提交任务时删除 `CreateVideo.audio` 连接；打开时保留完整音频链路。
- 默认设为无声，符合电商素材制作习惯；需要原生音轨时再勾选声音。
- 既有 0.78MP、3 秒 Turbo 记录中，有声约 102.6 秒、无声约 103.5 秒，差异约 0.9 秒，属于正常运行波动。声音开关对主采样速度影响很小，但无声可省去音频 VAE 加载、解码、封装及一部分显存占用。

## 5. 音频预览与媒体标识

- MP3：读取 ID3 APIC 内嵌封面。
- FLAC：读取 PICTURE 元数据块。
- M4A / MP4 音频：读取 `covr` 封面原子。
- 没有内嵌封面或格式无法提供封面：显示音乐渐变占位图。
- 图片不增加额外标识；视频沿用原有的中央播放符号；音频使用相同位置和风格的中央音乐符号。
- 放大预览仍使用原有图片 / 视频 / 音频播放器逻辑。
