## 2. 本次目标

本地 `minimax-h3-local` 不再要求用户理解 `0.7MP / 0.9MP`。前台按常用视频清晰度选择：

```text
360P
480P
720P
1080P
```

后台结合画幅自动计算目标总百万像素，再写入 ComfyUI 的 `ResolutionSelector.megapixels`。

同时保留原始 MP 输入能力，方便通过引用字段动态传值：

```text
0.3
0.7
0.78
0.78MP
```

## 3. 映射口径

清晰度档位表示目标短边：

- 横图：高度为360/480/720/1080；
- 竖图：宽度为360/480/720/1080；
- 方图：宽高均为对应数值。

计算公式：

```text
目标 MP = 短边² ×（长边比例 ÷ 短边比例）÷ 1,000,000
```

ComfyUI 节点随后会按工作流的 `multiple` 对宽高做模型所需的倍数对齐，所以最终输出可能略高或略低于理论尺寸。例如实测 `2:3 + 0.78MP` 输出为 `736×1120`。

| 2:3 | 0.1944 | 0.3456 | 0.7776 | 1.7496 |
| 3:2 | 0.1944 | 0.3456 | 0.7776 | 1.7496 |
| 3:4 | 0.1728 | 0.3072 | 0.6912 | 1.5552 |

| 9:16 | 0.2304 | 0.4096 | 0.9216 | 2.0736 |

注意：1080P，尤其是9:16、16:9和21:9，会明显提高显存、生成时间和失败风险。映射存在不代表当前显卡一定能在所有时长和模式下稳定完成，建议先用3秒 fast 测试。

## 5. 原始 MP 兼容规则

以下输入直接作为 MP 使用，不按360P/480P/720P/1080P转换：

| 输入 | 传给 ComfyUI |
|---|---:|
| `0.3` | 0.3MP |
| `0.3MP` | 0.3MP |
| `0.7` | 0.7MP |
| `0.7MP` | 0.7MP |
| `0.78` | 0.78MP |
| `0.9MP` | 0.9MP |

允许范围继承当前 `ResolutionSelector`：`0.1–16.0MP`。

这也保证了 v2.5.0 已保存的0.7/0.9配置升级后仍能继续使用。

## 6. 引用字段使用方法

AI 视频列的“清晰度（可引用字段）”仍保留右侧“+ 引用”。

例如数据表中有一列名为“输出清晰度”，每行可以分别填写：

```text
360P
480P
720P
1080P
0.3
0.78MP
```

在 AI 视频列中引用 `{输出清晰度}` 后，每行会读取自己的值。字符串解析发生在前台模板解析之后，因此下拉选项和引用字段最终走的是同一套 ComfyUI 协议逻辑。

比例字段同样可以引用，例如一行填写 `2:3`，另一行填写 `16:9`；清晰度档位会自动依据每行实际比例换算。

## 7. 对其他 Provider 的兼容

- 2K和4K选项继续保留，供原有 Lingwu 或其他模型使用；
- 清晰度到MP的自动换算只发生在 ComfyUI 工作流客户端；
- Lingwu 原有 `video_param_mapper.js` 没有被修改；
- `minimax-h3-local` 的 manifest 只声明360P、480P、720P、1080P；
- 如果把2K/4K交给当前 H3，会收到明确的“不支持清晰度”错误，而不会错误生成。

## 11. 第二阶段初步设计边界

第二阶段建议优先使用“工作流路由协议/注册方案”，不立即编写一个深度耦合具体模型的自定义 ComfyUI Python 节点。需要先确认：

- 目标工作流清单及各自输入能力；
- 首帧/尾帧节点的具体接口；
- 图片、视频、音频的优先级和互斥规则；
- 缺少某种素材时应报错还是回退；
- 切换工作流是在应用提交前完成，还是在单个 ComfyUI 图内完成；
- 输出类型和保存节点是否统一。

确认这些边界后，再决定是扩展 manifest 路由、增加应用侧路由器，还是开发真正的 ComfyUI 自定义路由节点。
